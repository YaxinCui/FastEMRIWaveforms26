# 把探测器延迟计算准备成可复用算子

本轮结论：**响应对象长期保留、需要重复计算时，缓存 TDI 算子有效；一次性
调用则没有明显的大幅收益。** 原型保持 FP64，未修改已安装的响应库或 FEW

## 原理

探测器处理分两步：先把两个引力波极化投影到六条星间链路，再将不同延迟的
链路信号组合成 TDI 通道。原版已经缓存轨道插值数据；本实验缓存的是特定
采样网格上的延迟与插值系数，不是“省去每次重新生成 ESA 轨道”。
[Katz 等人的响应论文](https://arxiv.org/html/2204.06633)介绍了这两个步骤。

固定轨道、时间网格、插值阶数和通道组合后，TDI 对六条链路信号是实线性的：

```text
cropped_XYZ = H × six_link_samples
```

每个输出只读取少量附近时刻的输入，因此 H 是稀疏矩阵，不必存一个巨大的
稠密时间×时间矩阵。不同引力波可以复用同一个 H；天空位置的变化仍由未修改
的原生投影计算处理。这里并不假设任意复数乘法能穿过整个响应过程。

[实现](../collaboration/linux/prepared_tdi.py)直接展开已安装版本的 Lagrange
有限插值公式，保留原来的 A/E 查表、各项符号及光行时的逐项减法顺序。
同一链路上的重叠插值区间先累加，再直接生成 CSR，避免大量重复坐标排序。
系数展开和求和重排会改变浮点舍入，所以验证的是数值一致性，不承诺逐字节相同。

特别需要保留物理约定：本版本采用同一时刻的光行时之和，而不是逐级递归延迟。
这是论文式 (20) 明确采用的引力波响应近似，不是发现了作者遗漏的循环。
本实验没有改变它，也不能用于认证激光噪声抑制。

## 为什么数据生命周期也影响速度

最初，为防止 Python 轨道与 C++ 已持有轨道不一致，每次建矩阵都重新校验
约 122 MB 的几何数组。结果虽然正确，首次处理 13 个基却比原版慢。

最终做法是在响应对象创建、首次交给 C++ 之前，就把几何数据变成不可修改
的 bytes-backed 数组。普通 NumPy 无法重新开启写入；替换数组、形状或配置
也会被检查拒绝。这样避免每次重复扫描大数组。创建时的复制成本仍要支付，
因此测试同时覆盖了“已经创建对象”和“把创建也计入”的情况。

## 实测结果

本机 CPU、短时 FEW 输入、13 个相位基，五组交替对照的中位数：

| 计时范围 | 原版 | 新方案 | 倍率 |
| --- | ---: | ---: | ---: |
| 已有响应对象，建矩阵＋处理整批 | 0.186 秒 | 0.133 秒 | 1.40× |
| 已有矩阵，处理整批 | 0.186 秒 | 0.068 秒 | 2.72× |
| 还计入响应对象创建，轨道已配置 | 0.262 秒 | 0.253 秒 | 1.03× |

最后一行只差约 3%，不能称为明显的冷启动加速。只处理一个波形时，计入
响应对象创建的新方案反而约慢 2.1 倍。这些范围均不包含 FEW 波形生成；
不能把倍率与上一轮相位优化相乘，也不是 GPU 性能结论。

默认矩阵的三个 CSR 数组共约 15.0 MB，不包含轨道、响应对象或构建峰值。
当前显式限制构建规模，没有验证把全年时序整体展开成矩阵的内存可行性。

## 精度证据与限制

两组实际正行/逆行相位基，加上新生成的 6 个独立相位 FEW 波形，都与原版
响应对照。默认配置最大加权全局相对误差 5.67e-14；逐通道最大 5.58e-12。
包括基函数输入在内的 96 项高斯似然对照，最大绝对差 3.49e-10。另测纯极化、
零信号、随机链路、脉冲、更改天空、采样间隔和插值阶数；7 个测试方法通过。
最终来源和结果审计通过 447 项检查。

这些是对既有离散算子的数值回归检查，噪声度量是固定合成 PSD；不是新的
物理模型验证、全年推断精度或真实噪声协方差认证。下一步应围绕长期复用、
分块内存控制和实际 GPU 工作负载继续实验。

本轮还保留了一个依赖接口缺陷：旧版显式传入六条链路数组的入口访问了未定义
属性，正常波形流程不走这个入口。该问题适合单独修复，未混入本轮优化。
